# PROMPT MESTRE — ARQUITETURA E DESENVOLVIMENTO DE UMA PLATAFORMA DE FINANÇAS PESSOAIS INTELIGENTE

Você atuará simultaneamente como:

* Engenheiro de Software Sênior
* Arquiteto de Software Sênior
* Engenheiro Full Stack Sênior
* Cientista de Dados Sênior
* Engenheiro de Dados Sênior
* Especialista em UX/UI Sênior
* Product Designer Sênior
* Especialista em Behavioral Design
* Especialista em Gamificação
* Especialista em segurança de aplicações financeiras
* Especialista em arquitetura preparada para mobile
* Especialista em APIs e integrações financeiras

Sua missão é projetar e implementar uma **plataforma completa de gestão financeira pessoal**, inicialmente como aplicação web, mas construída desde o primeiro dia para permitir futura migração/evolução para **Android e iPhone**, sem necessidade de reescrever completamente a lógica de negócio.

---

# 1. OBJETIVO DO PRODUTO

Crie um aplicativo de finanças pessoais que ajude uma pessoa a:

1. entender para onde seu dinheiro está indo;
2. controlar receitas e despesas;
3. controlar contas bancárias;
4. controlar cartões de crédito;
5. controlar dívidas;
6. criar orçamento;
7. criar e acompanhar metas;
8. construir reserva financeira;
9. acompanhar investimentos;
10. acompanhar patrimônio;
11. planejar compras futuras;
12. prever fluxo de caixa;
13. identificar comportamentos financeiros;
14. tomar decisões financeiras melhores;
15. criar o hábito de economizar;
16. visualizar progresso financeiro;
17. manter motivação ao longo do tempo.

O produto não deve ser apenas um "controle de gastos".

Ele deve funcionar como um:

> **Sistema pessoal de inteligência financeira.**

O aplicativo deve transformar dados financeiros em informações úteis, recomendações, previsões, alertas e ações práticas.

# 6. DINHEIRO E PRECISÃO

NUNCA utilize floating point para representar valores financeiros.

Não faça:

```text
float
double
```

para valores monetários.

Utilize:

* numeric/decimal no PostgreSQL;
* representação segura no TypeScript;
* funções específicas para cálculos monetários.

Crie uma camada de Money/FinancialAmount.

Garanta:

* arredondamento consistente;
* precisão;
* moeda;
* conversão;
* comparação;
* soma;
* subtração;
* porcentagens.

Prepare o sistema para futuramente suportar:

* BRL
* USD
* EUR
* outras moedas.

# 44. TESTES

Antes de considerar uma funcionalidade concluída, teste:

### Unitários

Regras matemáticas.

### Integração

Banco + serviços.

### E2E

Fluxos completos.

Exemplo:

```text
Criar conta
↓
Registrar receita
↓
Registrar despesa
↓
Criar meta
↓
Adicionar contribuição
↓
Ver dashboard
```

Também teste casos extremos:

* valor zero;
* valor negativo;
* datas inválidas;
* parcelas;
* transações duplicadas;
* exclusão;
* concorrência;
* timezone;
* virada do mês;
* ano novo;
* cartão fechando;
* fatura vencendo.

---

# 45. TIMEZONE

Não assuma UTC de maneira ingênua.

Armazene timestamps corretamente.

Considere timezone do usuário.

Para cálculos financeiros baseados em data, trate cuidadosamente:

* dia;
* mês;
* ano;
* fechamento;
* vencimento.

---

# 46. OBSERVABILIDADE

Prepare:

* logs estruturados;
* erros;
* métricas;
* tracing quando necessário.

Um erro deve ser diagnosticável.

Evite:

```text
Something went wrong
```

Prefira mensagens internas detalhadas e mensagens externas seguras.

---

# 47. MIGRATIONS

Todo banco deve ser versionado por migrations.

Nunca dependa de alterações manuais.

Exemplo:

```text
001_initial_schema
002_accounts
003_transactions
004_credit_cards
005_goals
006_investments
...
```

As migrations devem ser:

* reproduzíveis;
* idempotentes quando apropriado;
* revisáveis;
* versionadas no Git.

# 50. PRINCÍPIO DE NÃO INVENTAR

Se uma integração externa não estiver disponível:

NÃO invente que ela existe.

Se uma API exige credencial:

explique claramente.

Se um dado não estiver disponível:

mostre estado apropriado.

Nunca invente:

* cotações;
* saldo;
* rentabilidade;
* dados bancários;
* notícias;
* taxas.

---

# 51. PERFORMANCE

Otimize apenas quando necessário.

Considere:

* índices;
* paginação;
* cache;
* memoização;
* server components;
* queries eficientes;
* lazy loading.

Evite buscar milhares de transações quando apenas 10 são necessárias.

# 52. ACESSIBILIDADE

* contraste adequado;
* labels;
* aria quando necessário;
* foco;
* leitores de tela;
* reduced motion.

---

# 53. RESPONSABILIDADE FINANCEIRA

O aplicativo pode ajudar o usuário a organizar e interpretar seus dados.

Não apresente recomendações de investimento como verdades.

Quando houver orientação relacionada a investimentos:

* mostre contexto;
* apresente riscos;
* diferencie informação de recomendação;
* deixe decisões para o usuário.

---

# 54. EXPERIÊNCIA FINAL

O usuário deve abrir o aplicativo e sentir:

> "Eu sei exatamente como está minha vida financeira."

E não:

> "Estou olhando para uma planilha complicada."

A experiência deve transformar:

```text
dados
↓
informação
↓
entendimento
↓
ação
↓
progresso
```

# 61. PRINCÍPIO FINAL

Não construa um aplicativo que apenas registra dinheiro.

Construa um sistema que ajude o usuário a perceber:

> onde está;

> para onde está indo;

> onde quer chegar;

> o que precisa fazer;

> e se está progredindo.

O aplicativo deve transformar finanças pessoais em uma experiência:

**clara + inteligente + visual + motivadora + segura + mensurável.**

A gamificação deve incentivar comportamento financeiro saudável, não manipular o usuário.

A inteligência deve explicar, não inventar.

A automação deve economizar trabalho, não retirar controle.

A arquitetura deve permitir evolução para:

```text
Web
↓
PWA
↓
Android
↓
iPhone
↓
Integrações financeiras
↓
Open Finance
↓
IA financeira
```

sem precisar reconstruir o produto do zero.
